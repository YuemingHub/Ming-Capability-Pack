# Ming 演化记录

> 这份文档记录 Ming 从 v0.1 到今天的每一次关键演化——
> **不是"改了什么"（那是 changelog），而是"为什么改"和"当时怎么想的"。**
>
> 它是一份"决策考古学"档案：未来的维护者（包括十年后的自己）回头看，
> 能理解"为什么当时要这样设计"——而不是对着代码猜测"前人是不是疯了"。
>
> **维护纪律**：每个版本只记关键决策（不是所有变更）；写清 **tradeoff**（选择了什么、放弃了什么）；记录当时的**上下文**（以后回头看才知道为什么做这个决定）。

---

## 当前（进行中）: 验收协议 v1 — 可信交付层地基

**时间**：2026-08-23

**关键决策**：
1. 新增 `protocol.ts`：把 `verification` 和 `qualityBar` 从 Recipe 里散落的普通字段，升级为有版本号（`ACCEPTANCE_PROTOCOL_VERSION = 1`）、可独立校验、可独立回归的"验收协议"。
2. 新增 `acceptance-log.ts`：每次独立验收通过后，把结果结构化追加到 `ming-evidence/acceptance-history.jsonl`——这是"证据飞轮"的第一铲原始数据。
3. 新增 `ming_acceptance` 只读工具：查询每个方案历次验收通过率。
4. `resolver.ts` 装配阶段 fail-fast：坏协议在规划阶段就抛错，不拖到执行阶段。
5. `ming_auto` 把本次独立验证与**当前方案**的累计验收健康度一起展示给用户：信任层从后台机制变成可见交付体验。

**为什么这么做**：
- 战略规划的核心判断：护城河在信任层（质量门 + 验证 + 证据），不在执行层。
- 之前的 `verification` 只是散落在 Recipe 里的普通字段，没有版本号、没有校验、坏了要到执行时 verifier 跑 `default` 分支才崩。
- 之前的证据卡是"写后即忘"的死数据——从来没有被查询、聚合、反哺决策。
- 这一步的目标不是"加功能"，而是**把信任层从"代码里散落的字符串"变成"一等公民资产"**。
- 验收如果只在后台发生，用户无法感知 Ming 和裸宿主执行的差异；因此必须把"本次验收"与"历史健康度"变成完成汇报的一部分。

**Tradeoff**：
- 选择了 **纯函数 + 测试回归** 的轻量方式，而不是引入 DSL 或外部协议格式（YAGNI）。
- 选择了 **JSONL 追加**（原始数据），而不是预聚合表（灵活性让给未来）。
- 选择了 **不在 v1.0 做 MCP 解耦**（跟战略规划不同），理由是：单宿主上还没证明价值前，跨宿主是伪命题。
- 放弃了运行时 fail-fast 分支的单独测试（内置 recipe 全合法，触发不了），接受校验器测试 + 回归测试作为兜底。
- 健康度只展示**当前命中方案**，而不是把所有 Recipe 的历史混进单次任务汇报；减少噪音，保持用户只看到与本次交付相关的证据。

**测试**：全量 150/150 通过（基线 118 + 协议 16 + 回填 11 + 之前验证遗留 5）。

## v0.9.0: 双模式 big-project + 接入 DSH Marketplace

**时间**：2026-08（推断，基于 git log `44b82fe`）

**关键决策**：
1. 新增 `big-project` 方案（8 个 recipe 中最大的一个）：支持从 0 开发（骨架先行、分模块交付）和存量项目（修 bug / 加功能 / 迷茫给建议）。多步工作流：现状探测 → 动手实现 → 运行验证 → 交付说明。
2. 接入 DSH Marketplace 搜索（`dispatch.ts` 的 `searchMarketplacePlugins`）：能力缺口不再只搜 1024Store，优先走 Marketplace（无 key 无限流、带中文摘要）。
3. `dispatch.ts` 中间件自动装配：curated 优先 → 市场兜底 → 官方源自动装 / 社区源一句确认。

**为什么这么做**：
- 之前的能力装配闭环（v0.7）只能搜 1024Store，但 Marketplace 数据质量更高、有中文摘要。
- `big-project` 是第一个"复杂项目全流程"方案——之前的方案（整理文件夹、HTML 报表、个人网站）都是单步任务，不涉及"先探测再动手"的决策链。

**Tradeoff**：
- `big-project` 的 `stopAfter` 暂停机制（探测完等用户确认再动手）增加了交互复杂度，但避免了"盲改代码"的风险。
- Marketplace 搜索增加了外部依赖（网络 + API 可用性），但有 1024Store 兜底。

## v0.8.0: 能力推荐 + 工作流编排

**时间**：2026-07（推断，基于 git log `7883966`）

**关键决策**：
1. 新增能力推荐引擎（`recommend.ts`）：`rankCandidates` 按场景匹配度 + 热度排序，`buildRecommendationReason` 生成人话推荐理由。
2. 新增工作流执行器（`workflow.ts`）：多步工作流逐步执行、逐步验收、失败带坑位修法、`workflowFrom` 断点续跑。
3. 修复装配闭环缺陷（commit message 提到）。

**为什么这么做**：
- 之前的能力装配（v0.7）只是"搜到候选 → 展示给用户选"，没有排序和推荐理由。用户面对 5 个候选不知道该选哪个。
- 复杂任务（如"发布网站"需要建站→校验→发布三步）在单步委派中容易中途失败、用户不知道哪一步炸了、只能从头再来。

**Tradeoff**：
- 工作流引擎增加了执行层的复杂度（逐步探测能力、逐步验收、续跑逻辑），但换来了"用户不用自己排查为什么搞不定"。
- 推荐引擎的排序权重（场景命中 > 关键词命中 > 热度）目前是手工调参，没有用户行为数据校准。

## v0.7: 能力装配闭环（ming_install）

**时间**：推断，早于 v0.8

**关键决策**：
1. 新增 `ming_install` 工具：`mode=search` 搜 1024Store 候选 → 用户选定 → `mode=install` 执行安装 → 核对写入 → 重启指引。
2. 方案包开始声明能力依赖（`Recipe.capabilities`：`fs_*`、`excel_read`、`ppt_create` 等）。
3. 安全红线：只执行 `dsh plugin add` 形态；社区插件必须等用户一句确认；绝不把"没装成"说成"已装好"。

**为什么这么做**：
- 方案包声明了外部能力依赖（如读取 Excel 需要 `dsh-univer-office`），但早期版本只是"贴安装指引"让用户自己装。用户不会装、装不上、装完不知道怎么用——闭环断裂。
- 这是从"告诉你缺什么"到"帮你装好"的关键跃迁。

**Tradeoff**：
- 自动安装（官方源）和一句确认（社区源）的区分增加了安全护栏，但也增加了交互步骤。
- 安装后需要重启 DSH 才能生效——这是 DSH 插件机制的限制，Ming 用"重启后说继续"来弥补，但体验仍然有断点。

## 设计哲学确立期（推断，约 v0.5~v0.6）：薄转发器 + 硬编码触发词

**时间**：推断，项目早期

**关键决策**：
1. 执行层采用"薄转发器"架构：`executor.ts` 不自己写意图分析 / 步骤规划，而是把目标原样交给 Harness 原生子代理（`ctx.subagents.start`），只补资源预检、超时、产物校验三件可靠性小事。
2. 方案匹配采用硬编码触发词：`resolver.ts` 用 `RECIPES[].triggers` 做关键词匹配，后续加了 `TRIGGER_WEIGHT` 加权和 `RECIPE_SPECIFICITY` 特化度兜底。

**为什么这么做**：
- 薄转发器：DESIGN.md 明确写了"不重复造轮子"——Harness 原生子代理本身就是完整编码 Agent，能理解自然语言、自己拆步骤、用工具执行。再手写一套意图分析 + 步骤配方只会覆盖不全、与原生 LLM 重复、增加维护成本。
- 硬编码触发词：早期需要一种确定性高、零成本、不依赖 LLM 调用的"目标 → 方案"映射机制。关键词匹配在当时是最省事的选择；加权重是为了解决"做网站"同时命中 personal-site 与 big-project 的歧义。

**Tradeoff**：
- 薄转发器让 Ming 永远依赖宿主执行能力，自身没有不可替代的执行壁垒；但如果宿主能力持续增强，Ming 的"转发"反而成了最小成本路径。
- 硬编码触发词短期解决了方案映射问题，但长期成为方案命中率的最大障碍（8 个方案覆盖不了自然语言的全部表达方式）。

## 更早版本（v0.1 ~ v0.6）

**推断**（无一手资料，仅从代码结构推测）：
- `ming_auto` 核心执行链路（薄转发器：`executor.ts` → `ctx.subagents.start`）应该是最早建立的。
- `ming_plan` + `ming_clarify` 的策略选择（mvp-first / clarify-first）是后续迭代加入的。
- 8 个 Recipe 是逐步添加的（最早可能只有 `tidy-downloads` 和 `html-report`）。
- 证据卡（`evidence-collector.ts`）从早期就存在，但一直是"写后即忘"的状态。
