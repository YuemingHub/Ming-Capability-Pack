# Ming 演化记录

> 这份文档记录 Ming 从 v0.1 到今天的每一次关键演化——
> **不是"改了什么"（那是 changelog），而是"为什么改"和"当时怎么想的"。**
>
> 它是一份"决策考古学"档案：未来的维护者（包括十年后的自己）回头看，
> 能理解"为什么当时要这样设计"——而不是对着代码猜测"前人是不是疯了"。
>
> **维护纪律**：每个版本只记关键决策（不是所有变更）；写清 **tradeoff**（选择了什么、放弃了什么）；记录当时的**上下文**（以后回头看才知道为什么做这个决定）。

---

## 当前（进行中）: 需求地图——从「等用户点单」到「替用户盘需求」

**时间**：2026-08-24

**背景（用户指令）**：「你不要等我说，你要替我想，有人来都需要什么。我们提供什么。人的需求五花八门的。」——过去的需求侧是被动的：用户点任务 → 有方案就做、没方案就诚实失败。用户要求反过来：先把「来的人会要什么」盘成全景，对照供给侧找缺口、排优先级。

**关键决策**：
1. 新增 `docs/NEEDS_MAP.md`：需求全景地图（6 大类、26 个需求条目，全部用「人怎么说」的真实说法）+ 覆盖矩阵 + 缺口优先级。
2. 确立「四层提供」：①方案层（8 方案，自动验收）→ ②标准卡层（6 卡，先立「什么算好」）→ ③装配层（gap-probe + curated + 市场，缺能力有出路）→ ④诚实层（都没有就如实说）。
3. 缺口按「频率 × 可立标准 × 有出路」排优先级，我拍板不等用户：**P0** = 文字作品（简历/报告/文章）、总结提炼、表格数据整理；**P1** = 知识库、图片处理、格式转换；**P2** = 音频、自动化、采集（合规敏感）。
4. 维护纪律：新方案/标准卡先查矩阵，不重复造、只补空缺——矩阵让「缺什么」从凭感觉变成可审查。

**为什么这么做**：
- 「人来要什么」是需求侧资产，「我们提供什么」是供给侧能力——两者不对照，补功能就是拍脑袋（要么补了没人用，要么最痛的缺口一直空着）。
- 需求五花八门，但分类可穷尽到 6 大类；矩阵一查就知道「说得出 → 有没有路 → 差在哪」。
- P0 选择依据：文字作品和总结是小白开口频率最高的（写简历/写总结/写文章），且「什么算好」最可立（结构/要点/真实信息/无编造），验收可断言——最容易从标准卡变方案。

**Tradeoff**：
- 选择了「先盘需求、再排优先级」而不是「继续用户点一张做一张」：短期产出是文档不是代码，但避免重复造轮子（比如表格数据已有 excel_read 装配出路，不该从零造）。
- 选择了「缺口清单由我拍板」而不是全部列出等用户选：用户明确说「你不要等我说」——但 P0/P1/P2 的排序依据公开在文档里，可被推翻重排。
- 需求地图是策展资产（同 TASK_STANDARDS），不是功能承诺——矩阵里 🟡/🔴 如实标注「无方案无卡」，不因为「要显得全」而编造。

**测试**：无代码改动（纯文档资产），全量 187/187 保持。

## 当前（进行中）: 标准卡扩张——内容创作方向 3 张卡

**时间**：2026-08-24

**背景**：装配断路修复（gap-probe）后，「说得出口的任务」从「有装配出路」升级为「有验收标准」的下一步被点亮。用户直接点了三个高频内容创作任务：**视频制作、图文制作、把想法变成一个信息图**。

**关键决策**：
1. `TASK_STANDARDS.md` 增加 3 张标准卡（3→6 张）：
   - **infographic（把想法变成信息图）**：从方案 `infographic` 提炼，验收断言一一对应（file_exists *.svg / 含 <svg> / 含 viewBox）。
   - **graphic-cards（图文制作）**：从方案 `content-cards` 提炼，验收断言对应（含 content_absent 拦截工具痕迹）。
   - **video-production（视频制作）**：**知识资产先行**——先立「什么算好」，尚无 Recipe 实现。
2. **视频卡取「可执行下限」验收**：只有 `file_exists *.mp4/*.webm`（验证真实产出），质量门槛（开头能看懂/节奏/音画）全部人工验收——诚实红线：没有播放验证工具，绝不声称视频质量已验证。
3. 视频卡明确挂接装配兜底：目标含「视频/剪辑/动画」→ gap-probe 推断 video → 市场找候选 → 社区源一句确认。

**为什么这么做**：
- 信息图/图文已有方案与验收断言，卡从实现提炼，保证「标准卡与实现一致」的审校纪律（策展机制：诚实/小白可读/可执行三审）。
- 视频没有方案，但「什么算好」不能等方案齐了才立——标准是资产，方案是实现。先立标准，方案落地时照着标准做（SKILL.md 出口标记 ⏳）。
- 视频质量的验证上限是「磁盘事实 + 人工验收」：硬断言只能验「存在」，验不了「好不好」——诚实红线决定 verification 只放 file_exists，质量交给 qualityBar + 用户过目。

**Tradeoff**：
- 选择了「视频卡验收下限 = 文件存在」而不是「不立卡」：立卡让「做视频」有了明确交付标准与坑位，即便还没方案；代价是视频质量只能靠人工，不能像文件断言那样自动回归。
- 三张卡两张从方案提炼、一张资产先行——不强行给视频编造可自动验证的断言（那是新的说谎工具，违反第 5 节红线）。

**测试**：无代码改动（纯文档资产），全量 187/187 保持。

## 当前（进行中）: 战略收窄——从「能力包」到「方案层 + 交付体验层」

**时间**：2026-08-24

**背景**：对照 GitHub 生态做了一次诚实的盘底（`docs/ECOSYSTEM.md`）：
- 宿主 `deepseek-harness` 已原生提供插件/子代理/市场/安装；
- Agent Skills（SKILL.md）已成跨宿主技能包标准；
- 验证/质量门已是热门赛道（kimi-atlas 6-lens 确定性验证、supervisorLLM、dsh-verify、dsh-stage-gate 等）；
- 能力装配有 `dsh-plugin-autoevo`（Resolve→Search→Review→Deploy→Verify→Upgrade，成熟度远超本插件 dispatch）。

**关键决策**：
1. 项目定位收窄为「**DSH 上的方案层 + 交付体验层**」——不造宿主与生态已有的，只保留三块差异点：①自然语言→方案分流；②方案级验收协议 + 证据卡 + VTE；③小白交付体验。
2. **装配薄化（P1）**：`dispatch` 保持「轻装配」入口（curated 快查 + 一条命令能装上的市场候选），只对齐 autoevo 的诚信核心（未验证不报已装），不重复实现重型审查流程；`DispatchEntry.state` 状态机化（verified/pending/absent）。
3. **方案出口对齐 SKILL.md（P2）**：新增 `skill-md.ts` 纯函数 `exportRecipeToSkillMd`，内置方案可一键导出为标准 Agent Skill；内部匹配规则/验收协议保留私有（那是差异化资产）。
4. **吸收 dsh-verify（P3）**：verification 新增 `browser_acceptance` 断言——真实浏览器验收（JSON spec → Chromium → PASS/FAIL），本机未装配时**如实标记 skipped**（不谎报通过、不计失败、不阻塞交付）。

**为什么这么做**：
- 之前「什么都能做的能力包」定位在生态里是重复造轮子；收窄后每一个功能点都经得起「生态里有没有」的拷问。
- 浏览器级验收是「可信交付层」的最后一公里——文件断言验证不了「按钮点了有没有反应」，dsh-verify 正好补上，且不必自研。

**Tradeoff**：
- 选择了「对齐 + 吸收」而不是「运行时依赖」：autoevo / dsh-verify 均为低 star 未充分验证的项目，只参考其理念与调用方式，关键路径不设硬依赖。
- `browser_acceptance` 选择了 skipped（跳过）语义而不是失败/必装：诚实红线（跳过≠通过，明确标注「未执行」）与「不阻塞第一版交付」两条原则都保住；代价是缺失时验收是「部分完成」。
- 现有内置 web 方案暂不启用 `browser_acceptance`（机制就位，启用与否是产品决策，留给后续）；避免在无 dsh-verify 的默认环境改变既有验收语义。
- 方案包的 SKILL.md 出口第一版只做「生成文本」，不做目录/资源文件的整套打包（YAGNI）。

**测试**：全量 172/172 通过（基线 161 + dispatch 状态机 1 + skill-md 5 + browser-verify 5）。

## 当前（进行中）: 5-10 年视野——把战略落到「可迁移资产」上

**时间**：2026-08-24

**背景**：生态深挖有了战略级发现——
- 意图路由方向已被抢占：`Liber1917/skill-router`（跨平台纯 SKILL.md 路由，50+ 规则、pipeline/parallel/compose、8+ 平台）直接撞上原第一差异点「方案分流」；
- 产出预检有浅层对手：`skill-output-gate`（读总结文本做启发式检查，无协议、无执行验证、无证据沉淀）；
- **「小白交付体验」方向 GitHub 生态几乎空白**——现有验证/路由项目全是工程师向。

**关键判断（诚实版，以 5-10 年视角自问「今天做的东西会活吗」）**：
1. **插件形态会死**：宿主会变、能力会被内化；锁死单宿主的代码生命周期 = 宿主生命周期。
2. **路由/触发词匹配/轻验证会被内化**：模型原生理解能力会覆盖硬编码匹配，宿主会内嵌产物检查。让位生态，不投入。
3. **真正可能活到 5 年后的只有三样**：①开放验收协议（成为 Agent 交付「什么算好」的通用语言）；②「领域任务 × 什么算好」的策展知识（模型不会免费产生）；③交付体验的设计原则（让用户看懂/参与/可回查）。
4. **对小白**：今天只能帮到「装得上的人」；5 年后陌生小白会被宿主直接服务——我们能贡献的是「什么算好 + 怎么证明 + 证据可回查」的交付体验层，不是又一个执行层。

**本次落地（三份资产 + 一处代码）**：
1. `docs/ACCEPTANCE_PROTOCOL.md`：把 DSH 私有 `protocol.ts` 升级为**开放的、跨宿主的、独立文档化的验收协议规范 v1**（断言语言、passed/failed/skipped 三态语义、质量门槛、证据卡 schema、通过率 + VTE 指标、演进规则）。
2. `docs/DELIVERY_EXPERIENCE.md`：交付体验设计基准——「一条路：5 次对话」框架（入口→方向确认→不可逆暂停→交付展示→纠错回路）+ 平衡三原则（参与感=我说了算、认知负荷守恒、保质保量靠校准尺子）+ 工具词→人话词典。
3. `docs/TASK_STANDARDS.md`：领域任务标准库——标准卡 schema + 策展机制（诚实/小白可读/可执行三审） + 首批 3 张种子卡（整理文件夹/个人网站/发布网站，从真实方案提炼）。
4. **代码落地（第 4 次对话）**：`formatDeliveryReview` 交付展示——ming_auto 完成时给「产出数 + 独立检查 + 证据可回查 + 请你过目」，把验收判断权交还用户；失败任务不展示复盘邀请（给坑位指引）。

**Tradeoff**：
- 选择了「先立资产文档、再改代码」，因为 5-10 年能活的不是 DSH 代码而是资产；代码改造由设计基准驱动，而不是反过来。
- 交付展示第一版只做「计数 + 引用 + 邀请」，不做每件产出的用途描述（artifacts 只有路径，用途描述需要额外信息，YAGNI 留到交互数据积累后）。
- 三份文档保持「规范/基准」性质，不承诺实现——实现是否对齐由测试与代码 review 把关（如协议文档 §3 断言语言与 `protocol.ts` 一一对应）。

**测试**：全量 175/175 通过（172 + formatDeliveryReview 3）。

## 当前（进行中）: 交付体验层闭环——5 次对话全部落地

**时间**：2026-08-24

**关键决策**：
1. 补上「5 次对话」框架的最后一块：`ming_auto` 新增 `revision` 参数（纠错回路，第 5 次对话）——用户对交付展示不满意时，修正请求作为新输入重做，交付展示明确「已按你意见修正」。
2. **诚实红线延伸**：修正迭代绝不因「改过了」跳过验证——重新做、重新跑完整验收、重新展示证据。`revised` 字段非空时交付展示明示「重新做、并重新独立检查过（不是改完就算）」。
3. `DELIVERY_EXPERIENCE.md` 增加「实现状态」表：5 次对话（入口/方向确认/不可逆暂停/交付展示/纠错回路）全部有代码落点，设计基准不再是纸上承诺。

**为什么这么做**：
- 交付展示（第 4 次）落地后，用户看完「请你过目」说不满意——没有修正入口，这条路就断在最后一公里。
- 5 次对话是「小白走完能自己走」的交互骨架；补齐纠错回路后，体验层的核心承诺有了完整闭环。

**Tradeoff**：
- `revised` 选择「必填 string（空串=首次交付）」而非可选字段：与 DSH 工具输出 schema（字段级 required 恒 true）对齐，避免 schema 与类型不一致；空串语义清晰。
- 修正迭代不新建「修正模式」专用工具，复用 `ming_auto` 同一执行链路（resolve→execute→verify→evidence）：改动最小，且天然复用方案、质量门槛与验收断言。
- 无状态工具边界：`revision` 只是「修正请求 + 体验语义」，延续上次方案的上下文由调用方（主模型）维护——工具不自作主张记忆状态。

**测试**：全量 177/177 通过（175 + 修正迭代 2）。

## 当前（进行中）: 修复装配断路——通用能力缺口探测

**时间**：2026-08-24

**背景（用户追问暴露的真实断点）**：孩子说「给小猫画一幅画」/「做个视频」这类任务——未命中任何内置方案时，即使市场里有能装的能力（如视频剪辑 vox-director），`dispatch` 装配机制**根本不上场**（代码事实：`ming-auto.ts` 只在 `plan.recipeId && !plan.executable` 时触发装配）。方案内声明的能力缺口有出路，方案外/未命中方案的能力缺口是断路。

**关键决策**：
1. 新增 `gap-probe.ts`（`probeGenericCapabilityGaps` 纯函数）：从目标文本 + 资源文件名推断可能需要的能力（视频/图片/表格/PPT/数据库/知识库/发布），交给 `dispatch` 走市场找候选。
2. `dispatch` 新增 `forceConfirm` 选项：通用缺口是**低置信度推断**（可能需要 vs 方案内的确定需要），所以官方源也不自动装——全部走「回确认」一句确认（安全红线的延伸）。
3. `ming-auto` 未命中方案时接入：有 proposed 候选 → 提示「这个任务可能需要额外能力（候选 X），回确认帮你装」，并入 nextSteps；不阻断本次交付。

**为什么这么做**：
- 「小白说得出口的任务都能完成」的闭环缺最后一环：有方案 → 有装配；没方案 → 也应该有装配出路。
- 低置信度推断必须比方案内更保守：宁可让用户点一次确认，不静默装「可能需要」的能力。

**Tradeoff**：
- 通用探测只放高置信关键词（视频/剪辑/画/表格/发布等），避免给无关任务制造噪音；目标是「无命中就不提示」。
- 探测在未命中方案时触发一次真实市场搜索（网络失败优雅降级 not-found，已测试）；增加少量延迟换来「没能力也有出路」。
- 不把探测结果当验收：通用委派路径仍无验收断言，探测只影响「装配建议」，不影响验证诚实性。

**测试**：全量 187/187 通过（177 + gap-probe 10）。

## v0.9.1: 验收协议 v1 — 可信交付层地基

**时间**：2026-08-23

**关键决策**：
1. 新增 `protocol.ts`：把 `verification` 和 `qualityBar` 从 Recipe 里散落的普通字段，升级为有版本号（`ACCEPTANCE_PROTOCOL_VERSION = 1`）、可独立校验、可独立回归的"验收协议"。
2. 新增 `acceptance-log.ts`：每次独立验收通过后，把结果结构化追加到 `ming-evidence/acceptance-history.jsonl`——这是"证据飞轮"的第一铲原始数据。
3. 新增 `ming_acceptance` 只读工具：查询每个方案历次验收通过率。
4. `resolver.ts` 装配阶段 fail-fast：坏协议在规划阶段就抛错，不拖到执行阶段。
5. `ming_auto` 把本次独立验证与**当前方案**的累计验收健康度一起展示给用户：信任层从后台机制变成可见交付体验。
6. 北极星 VTE 埋点：`ming_acceptance` 输出月度「真执行且验证通过」的任务数与近 3 个月趋势（从验收历史聚合，不新增数据源）。
7. 证据卡内嵌 provenance 溯源：`goalHash`（目标 SHA-256 指纹，检测注入篡改）+ `source`（发起方）+ `recipeId`（OWASP 2026 方向的第一步）。

**为什么这么做**：
- 战略规划的核心判断：护城河在信任层（质量门 + 验证 + 证据），不在执行层。
- 之前的 `verification` 只是散落在 Recipe 里的普通字段，没有版本号、没有校验、坏了要到执行时 verifier 跑 `default` 分支才崩。
- 之前的证据卡是"写后即忘"的死数据——从来没有被查询、聚合、反哺决策。
- 这一步的目标不是"加功能"，而是**把信任层从"代码里散落的字符串"变成"一等公民资产"**。
- 验收如果只在后台发生，用户无法感知 Ming 和裸宿主执行的差异；因此必须把"本次验收"与"历史健康度"变成完成汇报的一部分。

**Tradeoff**：
- 选择了 **纯函数 + 测试回归** 的轻量方式，而不是引入 DSL 或外部协议格式（YAGNI）。
- 选择了 **JSONL 追加**（原始数据），而不是预聚合表（灵活性让给未来）。
- 选择了 **不在 v1.0 做 MCP 解耦**（跟战略规划不同），理由是：单宿主上还没证明价值前，跨宿主是伪命题。
- 放弃了运行时 fail-fast 分支的单独测试（内置 recipe 全合法，触发不了），接受校验器测试 + 回归测试作为兜底。
- 健康度只展示**当前命中方案**，而不是把所有 Recipe 的历史混进单次任务汇报；减少噪音，保持用户只看到与本次交付相关的证据。
- VTE 从已有验收历史聚合（整次任务 failed === 0 计一次），不新增事件流；先让数字可数，再谈精确。
- provenance 第一版只做最小溯源字段（goalHash/source/recipeId），完整安全溯源链（injection 单列、声明式/语义级区分）留到战略规划的 2027 里程碑。

**测试**：全量 161/161 通过（基线 118 + 协议 16 + 回填 11 + VTE 5 + provenance 4 + 信任可见 2 + 验证遗留 5）。

## v0.9.0: 双模式 big-project + 接入 DSH Marketplace

**时间**：2026-08（推断，基于 git log `44b82fe`）

**关键决策**：
1. 新增 `big-project` 方案（8 个 recipe 中最大的一个）：支持从 0 开发（骨架先行、分模块交付）和存量项目（修 bug / 加功能 / 迷茫给建议）。多步工作流：现状探测 → 动手实现 → 运行验证 → 交付说明。

- Marketplace 搜索增加了外部依赖（网络 + API 可用性），但有 1024Store 兜底。

## v0.8.0: 能力推荐 + 工作流编排

**时间**：2026-07（推断，基于 git log `7883966`）

**关键决策**：
1. 新增能力推荐引擎（`recommend.ts`）：`rankCandidates` 按场景匹配度 + 热度排序，`buildRecommendationReason` 生成人话推荐理由。

- 推荐引擎的排序权重（场景命中 > 关键词命中 > 热度）目前是手工调参，没有用户行为数据校准。

## v0.7: 能力装配闭环（ming_install）

**时间**：推断，早于 v0.8

**关键决策**：
1. 新增 `ming_install` 工具：`mode=search` 搜 1024Store 候选 → 用户选定 → `mode=install` 执行安装 → 核对写入 → 重启指引。

## 设计哲学确立期（推断，约 v0.5~v0.6）：薄转发器 + 硬编码触发词

**时间**：推断，项目早期

**关键决策**：
1. 执行层采用"薄转发器"架构：`executor.ts` 不自己写意图分析 / 步骤规划，而是把目标原样交给 Harness 原生子代理（`ctx.subagents.start`），只补资源预检、超时、产物校验三件可靠性小事。
2. 方案匹配采用硬编码触发词：`resolver.ts` 用 `RECIPES[].triggers` 做关键词匹配，后续加了 `TRIGGER_WEIGHT` 加权和 `RECIPE_SPECIFICITY` 特化度兜底。

**为什么这么做**：
- 薄转发器：DESIGN.md 明确写了"不重复造轮子"——Harness 原生子代理本身就是完整编码 Agent，能理解自然语言、自己拆步骤、用工具执行。再手写一套意图分析 + 步骤配方只会覆盖不全、与原生 LLM 重复、增加维护成本。
- 硬编码触发词：早期需要一种确定性高、零成本、不依赖 LLM 调用的"目标 → 方案"映射机制。关键词匹配在当时是最省事的选择；加权重是为了解决"做网站"同时命中 personal-site 与 big-project 的歧义。

**Tradeoff**：
- 薄转发器让 Ming 永远依赖宿主执行能力，自身没有不可替代的执行壁垒；但如果宿主能力持续增强，Ming 的"转发"反而成了最小成本路径。
- 硬编码触发词短期解决了方案映射问题，但长期成为方案命中率的最大障碍（8 个方案覆盖不了自然语言的全部表达方式）。
