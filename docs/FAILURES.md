# Ming 失败与弯路记录

> 这份文档记录 Ming 开发过程中走过的弯路、做错的决定、跌倒的方向。
> 它存在的唯一意义是：**让未来的我们（和新加入的人）不再重复同样的错误。**
>
> **维护纪律**（三条，违反就失去价值）：
> 1. **诚实**——不美化、不省略、不找借口。让你脸红的条目才是好条目。
> 2. **具体**——不说"我们学到了要测试"，而说"哪个测试没写导致了什么线上问题"。
> 3. **简短**——每个条目最多 5 行，2 分钟写完。不润色，不审批，想到就记。

---

## 2026-08-23: 战略规划过度远期，脱离当前现实

**背景**：产出了一份 10 年战略规划（四时代、十里程碑、六支柱、七护栏），但当前项目零用户、单维护者、强绑 DSH。

**错在哪**：规划用"有团队、有资源、有用户"的假设写了 2036 年的路线图，但 2026 年最紧迫的问题是"谁会用、为什么今天就要装"。规划的时间线（2027 第二宿主上线、2028 策展货架、2029 垂直领域包）对 solo maintainer 不现实。

**教训**：先活过 2026，再谈 2036。方向可以看十年，但行动只规划三个月。如果明年这个时候 VTE < 50、MAP < 10，这份规划就是废纸。

**修正**：把规划里的"可信立基期"拆成两步——v1.0 先让 DSH 上的用户离不开 Ming（信任可见），v2.0 再谈 MCP 解耦和跨宿主。

## 2026-08-23: 证据卡是"写后即忘"的死数据

**背景**：从 v0.7 起，每次 mint_auto 任务都会写证据卡到 `ming-evidence/evidence-<ts>.json`。但从来没有代码去读它、用它、反哺它。

**错在哪**：证据卡是"write-only"——写了就完了，从来不查询、不聚合、不参与下一次决策。战略规划说"证据是唯一可复利数据资产"，但实际实现把它当成了归档垃圾。

**教训**：数据资产的价值不在"存了多少"，而在"用了多少"。一个从来没被查询过的数据库，不是资产，是负担。

**修正**：本轮新增了验收结果回填（`acceptance-log.ts`）和健康度查询（`ming_acceptance`），让证据卡从"死 JSON"变成"可查询的累积历史"。但这才刚开始——证据卡仍然没有被主线决策流程（plan/auto）主动消费。

## 设计期（持续至今）: 硬编码触发词与 LLM 意图理解的矛盾

**背景**：`resolver.ts` 用关键词匹配（`RECIPES[].triggers`）做方案匹配。DESIGN.md 自己承认"硬编码的规则永远落后于真实需求"。

**错在哪**：明知道 LLM 的意图理解能力远强于关键词匹配，但还是选择了关键词——为了"确定性"和"零成本"。结果：8 个方案包覆盖不全，用户说"帮我做个完整网站"没有命中任何方案，走了通用委派。同时加了触发词加权（`TRIGGER_WEIGHT`）和特化度兜底（`RECIPE_SPECIFICITY`）来修修补补——越补越复杂，本质问题没解决。

**教训**：在"确定性"和"智能"之间选择确定性，短期是对的，长期会成为负资产。每多加一个硬编码触发词，就是在给未来的自己挖坑。

**当前状态**：未修正。方案匹配仍用关键词优先。战略规划没有提这个技术债，但它是方案命中率（护栏指标 ≥60%）的最大障碍。

## 设计期（持续至今）: 声明式校验的诚实局限

**背景**：`verifier.ts` 的验收断言是纯声明式的——`file_exists`、`content_match`、`content_absent`、`dir_nonempty`。它能验证"文件存在"和"内容包含某字符串"，但**不能验证"内容是否正确"**。

**错在哪**：战略规划自己指出"声明式校验是最大指标造假风险"。一个生成的 HTML 文件可以包含 `<html>`（content_match 过），但内容完全不可读、布局崩溃、链接全死——声明式校验看不出来。验证通过率 ≥80% 这个护栏指标，如果靠"放松校验到只检查最浅层"来达成，就是在自欺欺人。

**教训**：声明式校验是必要的第一层，但**绝不能是唯一的一层**。语义级验证（至少做到"用浏览器打开不报错""核心交互可执行"）虽然难，但如果不做，验证通过率就是一个虚荣指标。

**当前状态**：未修正。战略规划把语义验证放在 2030-2033。但我们今天就可以做一件低成本的事：**在验证通过率旁边，始终显示"本次校验深度（声明式/语义级）"**，让看数据的人知道这个数字的置信度。

## 设计期（持续至今）: 单维护者 bus factor=1

**背景**：项目从始至终只有一位维护者。战略规划把 bus factor 1→2 列为 P0 优先级。

**错在哪**：这不是"做错了什么"，而是"还没做但应该做"。单维护者的风险不需要解释——如果维护者离开，项目即死。更隐蔽的风险是：单维护者意味着所有决策没有第二双眼睛，代码 review 靠自己，方向判断靠直觉，疲劳时没人接棒。

**教训**：bus factor 1→2 不是"等有用户了再做"的事，而是"没有第二个维护者之前，项目随时可能归零"。它比任何功能都紧急。

**当前状态**：未解决。战略规划目标 2027H1 达成 bus factor 2。

## 推断（v0.7 之前）: 能力装配闭环的"先有鸡还是先有蛋"

**背景**（推断，非一手）：Ming 的方案包声明了能力依赖（如 `excel_read`、`ppt_create`、`publish_deploy`），但这些能力来自社区插件，用户可能没装。早期版本可能只是"贴安装指引"让用户自己装——用户不会装、装不上、装完不知道怎么用，闭环断裂。

**推断**：这催生了 v0.7 的 `ming_install` 能力装配闭环（search → install → verify → 重启指引），以及 v0.9 的 `dispatch.ts` 中间件自动装配（curated 优先 → 市场兜底 → 官方自动装 / 社区一句确认）。

**教训**：对小白用户，任何需要"你自己去装一下"的步骤，都是产品断裂点。要么全自动，要么诚实说"做不到"，不要留给用户一个他们完不成的任务。

## 2026-08-23: 验证做了，但用户看不见

**背景**：`qualityBar`、独立验证、证据卡、验收历史都已经存在，但原来的 `ming_auto` 汇报只把验证摘要夹在产物路径和下一步之间；累计通过率完全不展示。

**错在哪**：我们把"信任层"当成后端基础设施，而不是用户能感受到的产品体验。用户只看到"文件生成了"，看不到"为什么可以信任它"，于是 Ming 和宿主原生执行在用户心里没有差异。

**教训**：可信交付不是"后台做了验证"，而是"用户清楚看到验证了什么、历史上稳不稳"。看不见的质量门，没有产品价值。

**修正**：已修正（验收协议 v1 后）：`ming_auto` 在本次独立验证后展示该方案的累计验收健康度；无验证或无历史时不制造空区块。

## 2026-08-23: "薄适配层"很容易退化成没有理由安装的包装

**背景**：Ming 的执行器刻意不重造 Agent，而是把目标委派给 Harness 原生子代理。这是正确的架构克制，但也让它天然面临"为什么不直接用 DSH"的问题。

**错在哪**：一开始只证明了"可以转发执行"，没有同时证明"Ming 在结果质量、验证、失败恢复、证据上比裸宿主多了什么"。如果这些差异不持续可见，薄层就只是多一层调用链。

**教训**：薄层不是问题，**没有不可替代的约束和证据**才是问题。每一个新能力都要回答：它是否加强了"定义好、验证、可追溯"，还是只是在重复宿主执行能力？

**当前状态**：在修。验收协议、fail-fast、回填、健康度查询和用户可见验证构成第一层答案；仍需用真实用户的返工率验证它不是自我感动。
