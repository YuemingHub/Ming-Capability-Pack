# 领域任务标准库（Task Standards Library）

> **本文件是「领域任务 × 什么算好」的策展资产**——不是代码，是知识。
> 5-10 年视野下，模型能力会越来越便宜，但「对你来说什么算好」是领域知识，
> 模型不会自动知道，也不会因为算力增强而免费产生。这是少数会随时间增值的资产。
>
> 本库回答两个问题：
> 1. **一个常见任务，交付合格的标准长什么样？**（可声明、可验证、可讲给小白听）
> 2. **这套标准怎么持续积累与审校？**（策展机制，而不是一次性写死）

## 0. 与两份姊妹文档的关系

| 文档 | 回答的问题 |
| --- | --- |
| `ACCEPTANCE_PROTOCOL.md` | 「什么算好」用什么**语言**表达（断言、质量门槛、证据） |
| `DELIVERY_EXPERIENCE.md` | 怎么把这个标准**讲给小白听**并让他参与 |
| 本文档 | 具体**哪些任务、各自的合格标准是什么**（内容本身） |

## 1. 标准卡（Standard Card）schema

每个任务一张「标准卡」，全库统一结构：

```yaml
id:                 # 稳定标识（如 tidy-folder）
name:               # 任务名（人话）
when:               # 触发场景（用户怎么说会走到这里）
good:               # 一句话：合格 = 什么（交付后的「好」的状态）
verification:       # 硬断言（按 ACCEPTANCE_PROTOCOL.md §3；逐条人话 note 必填）
qualityBar:         # 质量门槛（§5：bar + checks + selfCheck）
pitfalls:           # 常见坑（小白最容易失败的点 + 修法）
review:             # 「交付展示」给用户看的人话要点（第 4 次对话的素材）
export:             # 可导出为 SKILL.md（跨宿主复用）
```

## 2. 策展机制（怎么积累）

1. **来源**：从真实方案（Recipe）提炼；从用户真实失败反馈提炼（FAILURES.md 是输入源）；从生态吸收（对齐开源标准如 agentskills.io）。
2. **审校**：每张标准卡必须通过三条审校：
   - **诚实**：每条断言都是「磁盘事实/可独立检查」，不是模型自述；无工具可验的断言不得声称「通过」；
   - **小白可读**：`note` 和 `review` 必须是不懂技术的人能看懂的句子（工具词→人话）；
   - **可执行**：验收断言在现有能力下能真的跑起来（跑不了就用 `skipped` 语义，不硬撑）。
3. **版本**：标准卡跟随验收协议版本演进；`id` 稳定，内容可修订（记录修订日期）。
4. **粒度**：宁少勿多。每张卡对应一个「小白会自己说出口」的任务，而不是一个工具功能。

## 3. 标准卡库（当前 6 张，审校通过）

> 首批 3 张（3.1~3.3）从现有方案包（`src/capabilities/recipes.ts`）提炼，保持与实现一致；`export` 标记表示已具备 SKILL.md 出口。
> 第二批 3 张（3.4~3.6）覆盖用户高频「内容创作」方向：信息图/图文两张从现有方案提炼，视频制作为知识资产先行（见 3.6 状态标注）。

### 3.1 整理文件夹（tidy-folder）

```yaml
id: tidy-folder
name: 整理下载/工作文件夹
when: 「帮我整理下载文件夹」「文件太乱了」「归档一下」
good: 整理完能立刻找到东西——不是把文件挪个地方
verification:
  - dir_nonempty（**/*）：目录结构应发生变化
qualityBar:
  bar: 这一轮就交付「整理完能立刻找到东西」，不是把文件挪个地方
  checks:
    - 分类规则合理：按「类型」而非大小/日期分，类别 5~8 个为宜，不碎片化
    - 保留可追溯性：文件名不被改写，移动后有汇总清单（类型→数量→新位置）
    - 边界情况处理妥当：隐藏文件、重名文件、正在使用的文件都不丢不覆盖
  selfCheck:
    - 随机抽 3 个文件，能否按分类逻辑立刻找到
    - 是否有一份「整理了什么、移到哪里」的汇总
    - 有没有文件被误删或覆盖（绝不允许）
pitfalls:
  - 先删后问 / 移动前不预览 → 铁律：先出分类计划，确认后再动
  - 文件名被改写导致找不到 → 保留原名，只换目录
review:
  - 我按类型整理了，分了哪几类、各多少文件
  - 有一份汇总清单，列出了每个文件去哪了
  - 请你抽查：随便找 3 个文件，看能不能立刻找到
export: ✅（可导出 SKILL.md）
```

### 3.2 个人网站（personal-site）

```yaml
id: personal-site
name: 搭建个人网站/主页
when: 「做个个人网站」「个人主页」「作品集」「博客」
good: 打开能直接展示的高质感网站——不是朴素占位版
verification:
  - file_exists（index.html）：应有首页
  - content_match（index.html 含 <html>）：应为有效 HTML
  - content_absent（index.html 不含 Lorem）：绝无占位文字
qualityBar:
  bar: 这一轮就交付「打开能直接展示的高质感网站」，后续迭代只做细节打磨
  checks:
    - 明确的视觉主题：统一配色（1 主色+1 强调+中性）、字号阶梯、卡片按钮样式
    - 首屏即亮点：hero 一句话说清「这是谁/做什么」+ 行动按钮，3 秒抓住注意力
    - 内容有真实质感：通顺真实中文文案，不用 Lorem 占位
    - 有存在感的交互：至少一处滚动/悬停/入场动效
    - 适配完整：移动端单列可读、桌面多列，导航无死链，控制台无报错
  selfCheck:
    - 第一眼是否「有设计感」而不是「像没做过样式」
    - 首屏 3 秒内能否说清「这是谁的网站、做什么的」
    - 有没有默认蓝链接、Times 字体、默认样式残留
    - 文案有无错别字、占位残留或假信息
    - 手机宽度（约 390px）下能否正常阅读
pitfalls:
  - 交付朴素占位版「先看看」→ 质量门槛要求第一轮就高质感
  - Lorem/假头像/假信息 → content_absent 断言拦截占位文字
review:
  - 网站做好了，首页/内页分别是什么、访问入口（文件路径）
  - 我检查过：首页存在、是有效 HTML、无占位文字
  - 请你过目：首屏是不是一眼说清「你是谁/做什么」？配色和排版顺眼吗？
export: ✅（可导出 SKILL.md）
```

### 3.3 发布网站（publish-site）

```yaml
id: publish-site
name: 发布网站/上线（一条龙：建站 → 校验 → 发布）
when: 「发布网站」「上线」「部署」「让别人能看」
good: 从零到可公开访问一条龙——没有站点先建一个，校验可打开，再发布，给出公开地址
verification:
  - file_exists（index.html）：应有站点首页
  - content_match（index.html 含 <html>）：应为有效 HTML
qualityBar:
  bar: 第一版交付=本地可运行 + 校验可打开；发布能力缺失不阻塞（如实说明上线路径）
  checks:
    - 站点真实可打开（本地路径或公开地址）
    - 有「怎么跑/怎么用/改了什么」的说明文档
  selfCheck:
    - 有没有真实执行「打开/启动」验证过
    - 发布是否成功、公开地址是否真实可访问；发布能力缺失是否如实说明
pitfalls:
  - 声称已上线但没验证 → 必须真实执行发布并给出可访问地址
  - 发布能力缺失硬撑 → 本地可运行即第一版，如实说明上线路径
review:
  - 站点已发布：公开地址 / 本地打开路径
  - 我检查过：页面可打开、是有效 HTML
  - 请你过目：浏览器打开看看，链接都能点吗？内容对吗？
export: ✅（可导出 SKILL.md）
```

### 3.4 把想法变成信息图（infographic）

> 从方案 `infographic`（文字变信息图/视觉表达）提炼，验收断言与方案一一对应。

```yaml
id: infographic
name: 把想法变成信息图
when: 「把这段话/这个想法变成一张图」「做个信息图」「一张图看懂」「流程图」「时间线」
good: 一段文字/一堆数据 → 站在一米外也能看懂核心信息的一张矢量图
verification:
  - file_exists（*.svg）：应产出 SVG 文件
  - content_match（*.svg 含 <svg>）：应为有效 SVG
  - content_match（*.svg 含 viewBox）：SVG 应有画布尺寸
qualityBar:
  bar: 这一轮就交付「能直接发出去的信息图」——站在一米外也能看懂核心信息
  checks:
    - 信息层次清晰：标题→要点→数字三层，大段文字先提炼成短句/关键词，不堆砌
    - 构图有呼吸感：留白充足，区块之间有视觉分隔，不挤成一团
    - 配色克制：1 个主色 + 1~2 个辅色，字号层级 3 级以内，移动端可读
    - 矢量输出：SVG 不失真，配 .html 预览页，双击可看
  selfCheck:
    - 一米外能否一眼看懂「这张图在讲什么」
    - 有没有大段文字堆砌（有就该提炼）
    - 颜色是否超过 3 个主色（超了就是花）
pitfalls:
  - 大段文字堆砌 → 信息图不是文稿，先提炼成标题/要点/数字
  - 颜色花哨超过 3 个主色 → 克制配色，一个主色带一两个辅色
  - 依赖外部生成 API 而产不出文件 → 用 SVG/HTML 纯文本产出，不依赖外部生成
review:
  - 图做好了：SVG 文件路径 + 双击可看的预览页
  - 我检查过：是有效 SVG、有画布尺寸、能正常打开
  - 请你过目：站远一米，能不能一眼看懂「这张图在讲什么」？
export: ✅（可导出 SKILL.md）
```

### 3.5 图文制作（graphic-cards）

> 从方案 `content-cards`（文章转多平台信息图：公众号封面 / 小红书 / 抖音）提炼，验收断言与方案一一对应。

```yaml
id: graphic-cards
name: 图文制作（文章/想法转多平台图文卡片）
when: 「做个图文」「图文卡片」「公众号封面/配图」「小红书/抖音图文」「把文章做成图」
good: 一篇内容/一个想法 → 一组可直接发布的低密度图文卡片，品牌化、零工具痕迹
verification:
  - file_exists（*.svg）：应产出 SVG 图文卡片
  - content_match（*.svg 含 <svg>）：应为有效 SVG
  - content_absent（*.svg 不含 Ming）：绝无工具痕迹/水印
qualityBar:
  bar: 这一轮就交付「能直接发布的低密度图文组」：公众号封面 + 小红书/抖音竖卡，品牌化、零工具痕迹
  checks:
    - 低密度：每张图一个信息点（大标题 ≤12 字 + 一句副标 + 至多 3 个标签），绝无段落文字
    - 平台尺寸：公众号封面 900×383（2.35:1）；小红书 1080×1440（3:4）；抖音 1080×1920（9:16）
    - 版式有设计感：边距 ≥ 8% 画布宽、层级「品牌→标题→副标→标签」清晰、对齐全卡统一、间距成梯队
    - 色彩克制：1 主色 + 1 强调色 + 中性色，文字对比 ≥ 4.5:1，不用 emoji
    - 品牌化：出现用户品牌名，绝无 Ming/插件/模型水印或「由XX生成」字样
    - 移动端可读：标题 ≥ 72px（1080 宽）、手机竖屏一眼看懂
  selfCheck:
    - 缩成手机屏幕大小，标题一眼能看清、没有小字堆叠吗
    - 有没有「由XX生成」这类工具水印或任何工具痕迹（绝不能有）
    - 每张图是不是只讲一个要点、内容密度会不会太高
pitfalls:
  - 段落文字堆砌（密度过高）→ 一卡一点，一卡讲不清就拆成多卡
  - 工具水印 /「由XX生成」→ content_absent 断言拦截，品牌化只出现用户品牌
  - emoji / 多重阴影 / 五颜六色 → 克制色彩，颜色留给标题与金句
review:
  - 做了几张图文卡片：公众号封面 / 小红书竖卡 / 抖音竖卡，文件路径
  - 我检查过：都是有效 SVG、无任何工具痕迹
  - 请你过目：缩成手机大小，标题看得清吗？有没有想改的配色？
export: ✅（可导出 SKILL.md）
```

### 3.6 视频制作（video-production）

> **状态：知识资产先行**——本卡先立「什么算好」的标准，尚未有对应 Recipe 实现（内置方案库里没有视频方案）。
> 验收断言取「可执行下限」（真实产出可播放文件），质量门槛以人工验收为主（诚实红线：没有播放验证工具，绝不声称视频质量已验证）。
> 当前能力缺口由通用装配兜底（gap-probe）给出路：目标含「视频/剪辑/动画」等词 → 市场找候选 → 社区源一句确认。

```yaml
id: video-production
name: 视频制作/剪辑
when: 「做个视频」「剪个视频」「把我的素材做成视频」「做个小动画/片头」
good: 素材/想法 → 一条真实可播放的视频文件，开头能看懂讲什么，结尾不突兀
verification:
  - file_exists（*.mp4 / *.webm）：应产出真实可播放的视频文件（注：视频「质量」无法用磁盘断言验证，此处只验证「真实产出」；质量由 qualityBar + 用户过目把关）
qualityBar:
  bar: 这一轮就交付「一条能直接播放、能看懂讲什么」的视频
  checks:
    - 有开头与结尾：开头 1 秒内让人知道「这条视频讲什么」，结尾不突兀
    - 有基础节奏：片段之间不硬切跳变；字幕/旁白（若有）与画面同步
    - 声音处理：有原声则音量不爆不闷；无原声时配合适背景音乐，或明确告诉用户「没有配乐」
    - 画面清晰：导出分辨率不低于 720p，时长与文件大小合理，不糊成一团
    - 诚实标注：哪些片段是 AI 生成、哪些是用户素材拼接，不冒充
  selfCheck:
    - 完整播放一遍：开头 3 秒能不能看懂讲什么
    - 有没有硬切 / 卡帧 / 音画不同步
    - 文件能不能双击直接播放（真实执行过播放验证）
pitfalls:
  - 声称「做了视频」但只给了制作脚本/思路 → 铁律：必须产出真实视频文件
  - 没有视频能力硬撑 → 如实说明缺什么能力，指引装配（gap-probe 已能给候选，社区源一句确认）
  - 静音视频不说明 → 无原声时明确告知用户「没有配乐，需要我加吗」
review:
  - 视频做好了：文件路径、时长、分辨率、音画情况
  - 请你过目：播放一遍，开头能看懂吗？节奏舒服吗？哪里要改？
export: ⏳（SKILL.md 出口机制就绪，待视频方案落地后打勾）
```

## 4. 积累路线（5-10 年视角）

- **第一年**：标准卡从现有方案提炼 + 从真实用户失败反馈沉淀（FAILURES.md 驱动）；当前 6 张 → 目标 20 张；
- **第二年**：标准卡开始独立于方案包被「领域化」消费——按领域分组（文件管理 / 建站 / 数据处理 / 内容创作），对接生态；
- **第三年**：标准卡通过 SKILL.md 出口进入其他宿主；验收协议 v2 按需演进；
- **五年后**：目标是「小白说得出口的常见任务，都有过审的标准卡」——这是任何单一模型都不自带的领域资产。

## 5. 不可做的事（红线）

- 不为「没有真实验收手段」的任务编造标准卡（会变成新的说谎工具）；
- 不把「工具教学」写进标准卡（那是教程，不是标准）；
- 标准卡里的每条 `note`/`review` 必须通过「小白可读」审校，出现工具词的卡不予通过。
