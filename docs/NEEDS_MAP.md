# 需求地图：人来要什么，我们提供什么（Needs Map）

> **这份文档是需求侧的全景盘点**——回答两个问题：
> 1. 小白用户（听不懂技术词、说不出工具名的人）会说出口的任务，到底有哪些？
> 2. 面对五花八门的真实需求，我们提供什么、不提供什么、缺口在哪、先补哪？
>
> 它是「供给侧」的家底（8 方案 + 9 标准卡 + 装配兜底）对照「需求侧」的覆盖矩阵。
> **维护纪律**：新增方案/标准卡前先查本矩阵——不重复造，只补空缺；新增需求类别时更新矩阵。
> 与 `TASK_STANDARDS.md`（什么算好）互补：这里管「有哪些需求」，那里管「每类怎么算好」。

## 0. 一句话：我们提供什么

**你说人话，我交付「做完的结果」——不是工具，不是思路，是能拿到手的结果。**
用四层兜住五花八门的说法：

| 层 | 提供什么 | 现状 |
| --- | --- | --- |
| ① 方案层 | 高频任务自动匹配方案：验收断言自动查「做完没做好」 | 8 个内置方案 |
| ② 标准卡层 | 还没方案的任务，先立「什么算好」的标准 | 9 张标准卡 |
| ③ 装配层 | 缺能力不卡死：市场找候选 + 一句确认帮你装 | gap-probe + curated + 市场 |
| ④ 诚实层 | 都没有 → 如实说做不到 + 给方向，绝不硬撑 | 通用委派 + 失败建议 |

## 3. 缺口优先级（我的判断，不等用户点单）

> 排序依据：**人说得出口的频率 × 有没有「什么算好」可立 × 有没有能力装配出路**。P0 是「高频 + 可立标准 + 有出路」，立刻值得做。

- **P0（高频空白，标准卡已补 3 张，下一步转方案）**：
  1. **文字作品**：简历、报告、文章、总结——✅ 标准卡 `writing-document`（3.7）已立；下一步做方案（触发词 + 验收断言 + 装配声明）。
  2. **总结提炼**：文章/聊天记录/会议纪要 → 要点——✅ 标准卡 `summarize`（3.8）已立；验收可断言（产出 markdown、无占位），忠实性靠人工过目。
  3. **表格数据整理**：汇总/清洗/核对——✅ 标准卡 `data-table`（3.9）已立；装配已有 excel_read 出路，数据一致性靠抽查人工核对。
- **P1（高频但需更多条件）**：
  4. **知识库问答**（装配有 knowledge_rag；验收 = 可问答 + 引用来源）
  5. **图片处理**（修图/去背景；验收难自动断言 → 资产先行卡 + 装配兜底）
  6. **格式转换**（PDF→Word、OCR；验收 = 产物文件存在 + 内容抽查）
- **P2（低频或需谨慎）**：
  7. **音频**（配音/转文字；依赖外部能力，验收弱）
  8. **自动化/定时**（验收强但实现重，且需宿主常驻）
  9. **数据采集**（合规敏感，需要用户明确授权与来源白名单，否则不碰）

## 4. 提供方式的分层承诺（怎么答「你们提供什么」）

1. **进门不问工具**：用户说人话，自动路由到方案/标准卡/装配兜底，不问「你想要什么格式」。
2. **交付的是结果 + 证明**：产物文件 + 独立验证 + 证据可回查 + 请你过目（不是「给你个思路」）。
3. **没有能力也给出路**：缺能力 → 市场候选 + 一句确认；没有候选 → 如实说明 + 方向。
4. **新需求进库有纪律**：新需求先查本矩阵 → 命中已有层就复用；不命中才立新卡（先立标准）或新方案（再补验收）。宁缺毋滥，避免「为了覆盖而编造验收」。

## 5. 红线（不可做的事）

- 不为没有真实验收手段的需求编造标准卡（视频已示范：验收下限 = 真实产出，质量交人工）；
- 不合规需求（无授权采集、冒充他人身份产出）不提供，如实说明；
- 「提供什么」永远比「用户以为我们要什么」诚实——做不到就明说做不到。
