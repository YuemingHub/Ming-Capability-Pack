# 交付体验设计基准（Delivery Experience Design Baseline）

> 本文件是「交付体验层」的正式设计基准——它回答一个问题：
> **怎样让一个陌生的、零基础的用户，通过自然语言完成一件真实的事，
> 全程既有参与感、又不被认知负荷压垮、还保质保量拿到结果，并且走完之后比开始前更懂这件事。**
>
> 它不绑定实现（可以是一个插件、一个宿主内置功能、或一套 SKILL.md），只定义体验的标准。

## 0. 问题诊断：小白面对 AI 生态为什么「一团乱麻」

工具、harness、agent 越来越多，但对新手来说这是**负资产**：

1. **选择过载**：工具词（MCP / Skills / Workflow / 子代理 / 插件市场）每多一个，新手就多一扇需要理解的门；
2. **任务被工具绑架**：新手带着任务来（「整理文件」「做个网页」），世界却在教工具；
3. **没有对照系**：不知道「什么算好」，模型说完成也无从判断真假；
4. **出错没有路标**：分不清是模型错、工具错、还是自己错，失败即迷宫；
5. **AI 越强，新手越难分辨真假**：老手能自证，新手只能信——幻觉藏得越深，新手越容易被坑。

**结论：新手缺的不是更多能力，而是一条「路」**——知道自己在哪、下一步往哪走、到什么程度算好、
出问题怎么出来、做完怎么证明没被坑。**工具堆是无数个点，我们要提供的是一条把点连成线的路。**

## 1. 平衡三原则（总纲）

参与感、低认知负荷、保质保量——三者不在总量上平摊，而在时间轴上错开：

1. **参与感 ≠ 交互次数，而是「我说了算」的感知。** 用户要的不是多操作，是每一次说话都被听见、且影响了结果。设计目标是：参与**少而关键、每次都被听见**。
2. **认知负荷守恒。** 用户的每一次交互都必须「花在刀口上」：要么换回方向确认，要么换回决策权，要么换回交付理解。系统承担全部幕后负荷，用户只承担台前少量但关键的负荷。
3. **保质保量靠「把尺子交给用户校准一次」。** 质量门槛不是系统私有，而是讲给人听、让人认可后才执行。「什么算好」由我们一起定，之后全程按尺子做、按尺子验。

## 2. 一条路：5 次对话框架

**第 1 次｜入口（零负荷）**
用户只说一句人话：「帮我把下载文件夹整理好」。系统不解释、不弹选项、不说工具词。

**第 2 次｜方向确认（参与感最高点，同时是需求捕获）**
系统给出「我的理解 + 一个关键权衡」，不是开放式问卷。

> 例：我会把下载文件夹按「图片/文档/安装包/杂项」四类归档，文件名自动规范化；重复文件单独放一边不动。**正式整理，还是先只出分类清单给你看？**

- 一次对话换回：方向对不对 + 深浅偏好。
- 小白说不清需求，但能说「对/改」——确认式需求捕获，负荷最低。
- 规则：**一次只问一个决策**。宁可多一轮，不在一轮里堆 3 个问题。

**第 3 次｜不可逆动作前暂停（保护性确认）**
在动用户代码、发布网站、删重复文件等不可逆/高成本动作之前，交底「接下来会动这些，确认继续」。次数要少：只在**不可逆、高成本、方向分叉**三种情况停。

**第 4 次｜交付展示（目前最薄弱、最该做的一块）**
完成不是一句「搞定了」，而是「给你看」：

- **做了什么**：产物清单（人话，讲每件产出的用途，不只给路径）；
- **我检查过**：独立验证的人话版证据（每条断言说「我看了什么、确认了什么」，失败/跳过如实标注）；
- **证据可回查**：证据卡位置（出了争议可回查，不是「我说了算」）；
- **请你过目**：把验收的判断权交还用户——「这些产出符合你的预期吗？哪里想调整？告诉我，我马上改。」

参与感落在「**我看懂了才说好**」——小白复核的不是技术，是「这符合我的要求吗」。

**第 5 次｜纠错回路**
用户说「不对」时，不给开放式文本框让他重新描述，而是给「我理解错在哪」的猜测让他点选/确认（「你是想要 A 还是 B？」）。单点修正，负荷最低，不把错误归咎于用户。

### 2.1 框架要点

- 全程不出现工具词（workflow/recipe/verification/capability/MCP…），只说「我会做这几件事」；
- 进度用讲故事：「正在整理文件 → 正在检查有没有重复 → 快好了」，不是「executing 3/7」；
- 5 次是「上限骨架」：简单任务 2 次就能完成（入口 + 交付展示），复杂任务也不超过这 5 类参与点；
- 用户随时可以跳过任何一次确认——默认值兜底，绝不因用户没回复而卡死。

### 2.2 实现状态（参考实现 Ming Capability Pack）

| 对话 | 代码落点 | 状态 |
| --- | --- | --- |
| 1 入口 | `ming_auto.goal`（自然语言一句话） | ✅ |
| 2 方向确认 | `ming_plan` / `ming_clarify` + Recipe `questions`（澄清问题 + 默认值 + 翻译） | ✅ |
| 3 不可逆暂停 | Workflow `stopAfter`（动代码前交底暂停，`workflowFrom` 续跑） | ✅ |
| 4 交付展示 | `formatDeliveryReview`（产出数 + 独立检查 + 证据可回查 + 请你过目） | ✅ |
| 5 纠错回路 | `ming_auto.revision`（修正请求 → 重新做 + **重新独立验证** + 交付展示明确「已按你意见修正」） | ✅ |

> 5 次对话全部有代码支撑；「走完能自己走」的第 5 次对话诚实红线：
> 修正迭代绝不因「改过了」跳过验证——重新做、重新验、重新展示证据。

## 3. 工具词 → 人话词典（第一版）

| 工具词（内部） | 对用户说的话 |
| --- | --- |
| workflow / 多步工作流 | 「这件事我会分几步来做」 |
| recipe / 方案包 | 「我打算这样帮你做」 |
| verification / 验收断言 | 「我检查过：」/「我确认了：」 |
| qualityBar / 质量门槛 | 「这次交付的标准是……」 |
| capability / 能力装配 | 「我准备好了需要的工具」 |
| skipped（未执行） | 「这项检查需要额外安装浏览器验收工具，本次没做（不影响交付，但不算通过）」 |
| evidence / 证据卡 | 「这次的记录保存在：」（可回查） |
| spawn / 子代理 / 委派 | 「我现在开始动手」 |
| resumeFrom / 续跑 | 「我们接着上次的继续」 |

## 4. 质量底线：不降，但可谈判

用户说「越快越好」与方案坚持质量门槛冲突时：

- **底线不降**：合格线不因「用户赶时间」而放松（否则我们变成又一个会撒谎的执行者）；
- **标准的内容可谈判**：把合格标准讲给人听，允许他在「A 标准（完整）」和「B 标准（简化，事后可能需回头补）」之间校准；
- 校准发生的时机在第 2 次（方向确认）——尺子在动手前定好，之后全程照做。

## 5. 这条路的验收自查清单（设计基准本身的验收）

任何实现（插件 / 宿主功能 / SKILL.md）宣称遵循本基准，须逐条自答：

- [ ] 小白从零开始、一句话入口能否走到交付？中间**不出现任何一个工具词**？
- [ ] 用户每次交互是不是都「影响结果」？有没有「为了显得智能而让用户点按钮」的交互？
- [ ] 「什么算好」是否在动手前被讲清楚、并被用户认可过一次？
- [ ] 交付展示是否包含：做了什么 + 独立检查过 + 证据可回查 + 请你过目？
- [ ] 用户说「不对」后，能否在**一次对话内**完成修正（给猜测让用户确认），而不是让用户重新描述？
- [ ] 走完之后，用户是否比开始前更懂「这件事为什么这么算好」？（不是一辈子靠保姆，是第一次有人带他走通这条路）

## 6. 与战略的关系

- 本基准是「**小白用户的可信交付层**」的产品化表达——入口一句话，沿途有路标（方向确认）、
  对照系（质量门槛+验收）、证据（证据卡）、救援（坑位指引+暂停确认）、教育（走完能自己走）；
- 它与「开放验收协议」（`ACCEPTANCE_PROTOCOL.md`）是一体两面：协议定义「什么算好、怎么证明」，
  本基准定义「怎么把这个证明讲给小白听、让他看懂并参与」；
- 5-10 年视野：交互模式会被更好的模型内化，但「让用户看懂、参与、可回查」的**设计原则**是长期资产，
  也是我们与「工程师向验证工具」最根本的差异。
